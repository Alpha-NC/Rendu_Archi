# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

**rendu-architectural** — **RIF-App** : application conversationnelle qui génère des rendus architecturaux photoréalistes à partir d'exports Revit et d'une photo de site, avec boucle de correction par annotation, pour Évariste Blasco (architecte, Biarritz). Implémentation du **Framework RIF** (`rif-framework/`), pas un remplacement de celui-ci.

Remplace le formulaire V2 (7 étapes, rejeté par le client comme « trop contraignant ») et prépare la bascule progressive depuis le Custom GPT V1 (« GPT RIF »), qui reste le filet de sécurité jusqu'en Phase 1.

Voir `docs/prd-generateur-rendu-v2.md` (V1.3) pour la spec complète et `rif-framework/Implementations/RIF-App/DECISIONS.md` pour les décisions d'architecture déjà tranchées (Phase 0A). `docs/PRD_RIF_V2_GEOMETRY_FIRST.md` complète le PRD V2.1 pour le workflow geometry-first (source modèle 3D, extraction, pack de contraintes, deux `OutputType` perspective/axonométrie, `TEMPORARY_PROJECT_ASSETS` — ADR-021/022, D-20/D-21) : format 3D et fournisseur d'extraction non figés, formats candidats RVT/FBX/DWG/DXF/DGN/OBJ/STL/IFC. **Formulation de fidélité officielle : « Maximiser la fidélité architecturale et réduire fortement les dérives géométriques » — jamais de garantie de 100 % ou de fidélité parfaite.** `docs/RIF_BACKEND_CONTRACTS_V2.md` décrit le contrat backend réel (routes, erreurs, états frontend exploitables, gaps connus) pour construire le frontend sans deviner ; `docs/PRD_RIF_V2_Geometry_First_UX_UI_Desktop_v2.1.md` guide l'UX/UI Codex. **Frontend reconstruit en desktop workspace** (`feat/rif-ux-ui-desktop`, commits `66a182e`/`693c1b7`) : `ProjectCockpit.tsx`/`ProjectDashboard.tsx`/`AppShell` remplacent l'ancienne interface minimale — audité le 18.09.2026 (soir), aucune sur-promesse trouvée (D-21).

Stack : Next.js 16 (App Router) · TypeScript · Tailwind CSS 4 · Neon PostgreSQL + Neon Auth (Managed Better Auth) + Vercel Blob (PRD V2.1, D-19), hébergé sur Vercel.

## Architecture — points critiques

- **Backend applicatif propre**, contrairement à la V2 : ce dépôt contient l'authentification, la machine à états et les appels serveur (Route Handlers/Server Actions). Il n'y a **plus de n8n** dans le chemin de production de RIF-App — le webhook V2 (`keALNdFoFMNT1Sxk`) est abandonné.
- **Authentification individuelle obligatoire** (Neon Auth) — plus de mot de passe unique partagé. **Aucune RLS** : PRD V2.1 §16.3, « le navigateur ne se connecte jamais directement à Neon » — la défense en profondeur reste `verifierProprietaire` côté Route Handler. Voir `proxy.ts` (convention Next.js 16, délègue à `lib/auth/server.ts`).
- **fal.ai est appelé directement depuis ce backend** (`fal-ai/nano-banana-pro/edit`), sans service intermédiaire séparé — voir DECISIONS.md D-05.
- **Le LLM ne pilote jamais directement une transition d'état ni un appel au moteur d'image.** Il propose ; seul le backend (`lib/rif/etat-machine.ts`) vérifie les préconditions et applique. Ne jamais dupliquer ces vérifications côté client ou les considérer suffisantes côté prompt seul.
- **ProjectState** (`lib/rif/project-state.ts`) est la source de vérité opérationnelle, distincte de la conversation. Une révision confirmée est immuable ; toute modification crée une nouvelle révision. Une génération est impossible sans révision confirmée (critère d'acceptation §22 du PRD, testé dans `lib/rif/etat-machine.test.ts`).
- **Aucune clé d'API dans ce dépôt** — `DATABASE_URL`, `NEON_AUTH_COOKIE_SECRET`, `BLOB_READ_WRITE_TOKEN`, Anthropic/LLM et fal.ai restent des secrets serveur uniquement (`ANTHROPIC_API_KEY`, `FAL_KEY` — jamais préfixés `NEXT_PUBLIC_`).
- **LLM multimodal : Claude Sonnet 5** (`claude-sonnet-5`) pour le dialogue, l'extraction du ProjectState et l'analyse des sources — décision D-06, voir `docs/decision-llm-multimodal.md`. Chaque génération doit enregistrer la version exacte du modèle utilisé (PRD §21).
- **Un appel d'outil n'existe que sous forme de `tool_use` réel.** Le prémortem du 02.09.2026 identifie comme échec le plus probable un modèle qui *décrit en texte* l'appel qu'il voudrait faire (bloc de code JSON) sans jamais l'émettre — l'utilisateur croit alors une génération lancée qui ne l'est pas. Ne jamais déclencher une action à partir de texte parsé : voir `lib/rif/appel-outil.ts`.
- **Le contrôle qualité ne produit qu'un verdict PROPOSÉ, jamais autoritaire.** `lib/rif/controle-qualite.ts` implémente la grille officielle LIB-002 (18 critères depuis le Lot 1 RenderTarget — `elements_inventes`/`photorealisme` ajoutés, 5 états dont `non_evalue`) et le garde-fou d'export (PRD §15.3) : seul `verdict_human` (jamais `verdict_proposed`) autorise un export administratif, et uniquement sur `'validation'` sans réserve. Le prémortem désigne ce point comme l'échec le plus dangereux (#3) — ne jamais faire raccourcir ce chemin par une génération de code future.
- **RenderTarget/OutputType/QualityProfile (D-22, ADR-022 précisé Lot 1)** : `lib/rif/render-targets.ts` — une cible de rendu (`render_targets`, neon/migrations/0002) regroupe les générations qui visent le même résultat (« Perspective entrée », « Axonométrie générale »...), avec au plus une génération canonique PAR CIBLE (plus l'ancien mécanisme dossier-large pour les générations legacy sans cible, jamais mélangés). `OutputType` a exactement deux valeurs (`PHOTOREALISTIC_PERSPECTIVE`/`PHOTOREALISTIC_AXONOMETRY`) et détermine le `QualityProfile` (sous-ensemble prioritaire de la grille LIB-002) appliqué au contrôle qualité — jamais envoyé par le frontend, toujours dérivé côté backend.
- Le Framework (`rif-framework/Framework/`) n'est **jamais modifié depuis le code applicatif** — c'est un non-objectif explicite du PRD (§25). Exception ponctuelle et documentée : ADR-021/D-20 (workflow geometry-first, 18.09.2026), autorisée explicitement par l'utilisateur pour cette seule mission — ne pas généraliser sans autorisation équivalente.
- **Geometry-first (ADR-021, D-20) : la source modèle 3D fait autorité sur la géométrie quand elle a été réellement extraite — jamais par sa seule présence.** `lib/rif/geometrie-3d.ts` refuse honnêtement toute extraction tant qu'aucun fournisseur n'est configuré (`EXTRACTION_PROVIDER_NOT_CONFIGURED`) : ne jamais simuler un résultat géométrique. Format 3D non figé (RVT candidat principal) — ne jamais coder en dur une dépendance exclusive à `.rvt`.
- **Une correction (`corrigerRendu`) exige une `categorie` parmi 6 valeurs figées** (`MATERIAL`/`LIGHTING`/`VEGETATION`/`LOCAL_ENVIRONMENT`/`ARTIFACT_REMOVAL`/`MINOR_PRESENTATION`, ADR-021) — voir `lib/rif/geometrie-3d.ts::estCategorieCorrectionValide`. Toute autre valeur est refusée : il n'existe pas de 7e catégorie « changement architectural », le refus lui-même est le garde-fou. Ne jamais ajouter une catégorie qui légitimerait une modification de volume/toiture/ouverture/implantation comme une correction locale — cela exige `reprendreDepuisSources`.

Combinaison non documentée par ENG-004 (Présentation générative) → aucune réduction, jamais d'invention de règle.
- `lib/rif/contraintes-libertes.ts` (+ `.test.ts`) — D-17, matrice Contraintes & Libertés (PRD §9.4A, §24A) : une propriété absente de la matrice vaut `locked` (la liberté créative n'est jamais implicite), la plus restrictive prévaut, et la géométrie d'un élément structurel ne descend jamais sous `strict`. §24A.3 : une liberté déclarée (`controlled`/`creative`) sans `authorized_by` n'a aucun effet ; `libertesEnAttente`/`autoriserLibertesEnAttente` portent le cycle proposition → confirmation.
- `lib/rif/prompt-technique.ts` (+ `.test.ts`) — construit le prompt technique réel envoyé à fal.ai (ENG-002 pour une génération, ENG-003 pour une correction). Le LLM conversationnel ne fournit jamais ce texte lui-même (PRD §9.5).
- `lib/rif/prompt-conversationnel.ts` — prompt système de l'assistant conversationnel : les 11 principes non négociables (PRD §4) + le plan de collecte déjà calculé par `collecte-conditionnelle.ts` (le modèle exécute ce plan, il ne déduit jamais lui-même les règles ENG-004) + les schémas d'outils, délibérément minimaux (`genererRendu` n'accepte aucun prompt du modèle).
- `lib/rif/extraction-project-state.ts` (+ `.test.ts`) — D-15 : fusionne dans le ProjectState une mise à jour minimale proposée par le modèle (valeur + statut), en complétant seul les métadonnées de traçabilité (source_id, authority, validated_at). Une valeur déjà `validated` n'est jamais dégradée par une mise à jour `provisional` — jamais silencieusement, toujours journalisée. Le modèle peut aussi proposer des entrées `contraintes_libertes` (§24A.3) : la fonction lui interdit structurellement d'y inscrire `authorized_by`/`authorized_at`, et fait repartir en attente une autorisation déjà accordée si la proposition l'élargit (`elargitLaLiberte`).

Ne boucle pas encore automatiquement pour renvoyer un `tool_result` au modèle et obtenir un message de clôture rédigé par lui — l'historique persisté ne porte que du texte, jamais les blocs tool_use/tool_result bruts.
